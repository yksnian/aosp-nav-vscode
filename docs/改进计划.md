## 0. 结论摘要

1. **核心链路（Java jar 注入）是完整的、能用的**：根检测 → `out/soong/.intermediates` 扫描 → 过滤/排序 → 写 `java.project.referencedLibraries` → 关 Gradle/Maven importer → Eclipse 元数据护栏，六步都有实现和单元测试覆盖（纯逻辑层）。
2. **真正的短板不在"能不能跳"，而在三处**：
   - **多工作区/多根**的调度是全局布尔互斥，第二个树会被静默丢弃（`src/extension.ts:50-51`）；
   - **缓存从不感知重新构建**，重建后引用的 jar 可能已不存在（`src/core/cacheModel.ts:21-27` + `src/extension.ts:71-80`）；
   - **缺少 Java 源码根注入**，跨模块跳转落在反编译 jar，而不是可编辑的 `.java`（nvim 版已有，见 `java/source_roots.lua`）。
3. **能力缺口按平台可分两类**：
   - **可移植**：C/C++（clangd + CDB 链路）、Java `sourcePaths`、KLS 残留进程治理、扫描进度/取消；
   - **受 VS Code 平台限制**：clangd 没有 nvim `lspconfig` 那样的"启动前同步改 opts"钩子，只能"预写 CDB + 写 `clangd.arguments` + 重启 LS"；fwcd KLS 全树 `addWorkspaceRoot` 遍历是 LS 自身缺陷，插件改不了，只能规避（multi-root / 提示）。
4. **建议先做一批低风险、可立即合入的修复（Wave 0，约 150 行）**，再做缓存与调度（Wave 1），然后才动两个大特性（Java 源码根、C/C++，Wave 2），最后做架构收敛（Wave 3）。大特性都必须先在真树 + 当前 `redhat.java` / clangd 扩展版本上做 spike 验证，再全量实现。

### 1.3 一次"注入"的完整链路（`src/extension.ts:47-153`）

1. 打开文件 → `detectAospRoot` 向上找 `out/soong/.intermediates`（`src/androidRoot.ts:11-20`）。
2. 全局互斥 `running` + 每根会话 `phase`（`src/extension.ts:25-27, 50-51`）。
3. `applyCompat`（两把 importer 开关 + `java.import.exclusions`）、`applyHygiene`（全局 watcher/search 排除）。
4. 读缓存 `jars-<djb2(root)>.json`，命中即跳过扫描（`src/extension.ts:71-80`）。
5. 未命中 → `scanSoong`（`src/core/scanner.ts:15-35`）→ `applyDirPriority`（`src/core/selector.ts`）→ 写缓存（tmp+rename）。
6. Kotlin 分支（可选）：写 per-root jar 列表 + 全局 dispatch 脚本（`src/kotlin/classpathChannel.ts:138-222`）。
7. 写 `java.project.referencedLibraries`（`src/jdtls/settingsChannel.ts:35-84`），失败保留会话可重试。
8. 状态栏 / 首次注入提示 / 输出通道日志。

## 3. 横向参照 aosp-nav.nvim

### 3.1 Java

| 能力 | nvim 版 | VS Code 版 | 差距结论 |
| --- | --- | --- | --- |
| jar 采集与过滤规则 | `java/jars.lua`（59KB，含 make 档、bazel 档、`collect_aosp_jars.sh`） | `core/scanner.ts`（仅 soong 档） | **make-era 采集缺失**：VS Code 版只探测目录存在性（`src/assets` 无 make 实现），`resources/defaults.json` 里的 `makeJars/makeBlacklist` 从未被消费 |
| 源码根注入 | `java/source_roots.lua` + `source_inject.lua`：显式写 `java.project.sourcePaths` 以压过 lib 顺序 | 无 | **最关键差距**：跨模块跳转落反编译 jar（nvim README Features 明确写"lands in real .java sources"） |
| 多实例/会话冲突 | `java/instances.lua`、`session_conflict.lua` | 无（VS Code 每窗口独立扩展宿主） | 平台差异，VS Code 侧不需要 |

| Eclipse 元数据 | `java/import_exclusions.lua`（16KB） | `eclipseGuard.ts` + 状态机 | 两版都处理；VS Code 版有更明确的"一次性 clean+reload"收敛逻辑，nvim 版有更细的排除规则，可互相对照补齐 |

- **启动前预写 CDB**：注释明确"clangd 启动时目录不存在 → `--compile-commands-dir` 被整体忽略；启动后写出的 CDB 不会被会话内重载"，因此在 `configure(opts)` 阶段同步 `ensure_entry`。

- 条目按"用户打开过的文件"增量 upsert，整文件重写（几十条，代价可忽略）。

VS Code 版：**零实现**。这是最大的功能空白，也是最有价值的移植对象。

## 6. 风险与"不做什么"

**风险**

1. **平台差异被误判为缺陷**：clangd/KLS 的启动时序在 VS Code 里没有 nvim 的钩子，W2 的两个特性都可能出现"首次打开仍不对、重启后正常"。必须在 README 明确写出，否则会被当成 bug。
2. **全局设置写入**：`compat.ts`/`workspaceHygiene.ts` 有意写全局层（`import.exclusions`、`watcherExclude`、`search.exclude`），在多窗口场景下会互相触发配置事件；P2-1 的 `SettingsWriter` 是收敛手段，在此之前不要新增全局写入点。
3. **`sourcePaths` 注入不可逆地关闭 jdt.ls 逐文件推断**：这是 nvim 版实测结论；若列表不完整，用户会从"跳 jar"变成"跳不到"，属于体验倒退。必须先 spike。
4. **缓存并发**：W1 引入按根并发后，同一棵树的两个窗口仍共享 `globalStorage`；现有 tmp+rename 可保正确性，但需要保留。
5. **基线版本提升**：Remote-WSL / 便携版用户的 VS Code 版本可能较旧；`engines` 抬升前先确认（README 已有 WSL FAQ，说明这是真实使用场景）。

**本轮明确不做**

- 不替换 jdt.ls（继续走 invisible project + referencedLibraries 路线）。
- 不引入 Gradle/Maven 解析（AOSP 的 `build.gradle` 是噪声，不是入口）。
- 不重写 jar 选择规则（`scanner`/`filters`/`selector` 的规则与 nvim 版共享，属稳定资产）。
- 不与 nvim 版统一运行时缓存目录/格式（两者缓存键、生命周期不同；只共享 `defaults.json` 规则数据）。
- 不在本轮做 Windows 专属路径（Kotlin sh 脚本、孤儿进程判定），先记录为"未验证"。
